Goal: Deliver M2 — schema live, LA place data loaded and queryable, provenance demonstrable — on the classes-first model of ADR-0019.

Architecture: Postgres is the seam. Python writes whole scraped classes into its own tables; Laravel re-judges each one and writes the live tables. Three database roles enforce the boundary, and the public site reads views it has no permission to bypass.

Tech Stack: PostgreSQL 16 + PostGIS 3.4, Laravel 13 (PHP 8.3), Python 3.11, Docker Compose, Terraform.

What M2 owes the client, and how this plan pays it

The contract says: "Database deployed including dated occurrences and geocoding. Los Angeles bulk place data loaded and queryable. Provenance model in place." Two of those phrases predate ADR-0019 and need answering honestly rather than quietly.

Contract phraseHow it is metHonest caveat
Database deployedYes — all tables, three roles, public views—
Dated occurrencesClasses carry starts_on / ends_on at 90% coverage, and date filtering worksNo per-date expansion. That needs days, which no source provides — 0% on endpoints. Expanding a range without days would be inventing dates. Raise with the client
GeocodingVenues geocoded, coordinates gate publicationAutomation resolves ~43% of classes; the rest is a finite venue queue (~350 names)
LA bulk place data loaded and queryableOverture LA loaded, queryable, and used as the venue gazetteerIt is no longer the spine. Same data, different job
Provenance model in placeEvery live class links to its scraped row, its raw payload, its source and its fetchField-level claims are retired. Provenance is per row plus a per-field evidence map

The demo proves it: one class walked from the public page back to the raw JSON the source returned, plus a radius query on real data.

Global Constraints

  • Python proposes, Laravel decides. Nothing Python writes appears on the site without Laravel judging it.
  • Three roles: asd_pipeline, asd_app, asd_web. Every migration grants as well as creates.
  • sources is the one shared table — Laravel owns the registry and the terms verdict, Python updates health and yield only. Column-level grants.
  • Only an admin sets a terms verdict. Not editor, not reviewer, never Python.
  • Politeness is not a terms question. One request per host, 2s apart, robots honoured, honest non-rotating user agent; 401/403/429 is terminal for that host — regardless of ADR-0001.
  • Two tables are named carefully: fetched_pages (crawl bodies) and content_pages (CMS). Never both pages.
  • No occurrences table. A date range is not a schedule.
  • Nothing is deleted by a crawl. Absence is flagged, never actioned on one run.
  • Measured reality: endpoint sources give name 100%, age 100%, dates 90%, description 98%, days 0%, price 0%. Provider websites give the opposite. Nothing may assume a field is present.

Task 1: Settle the three open items

Files: Create docs/superpowers/specs/2026-09-08-open-items-resolved.md

  • Step 1: Category assignment

Nothing currently assigns a category, and hubs, filters and search all need one. Decide between: Python proposes from the class name and description; an editor confirms in review; or categories are assigned per source. Record the decision and the fallback for an unmatched class.

  • Step 2: Kid-relevance threshold

ages 7–99 is an adult class in a mixed catalogue. src/kid_relevance.py exists; the rule does not. Decide the cutoff — a candidate is age_min <= 17 and age_max - age_min <= 30 — and record what happens to a class that fails it: rejected, or held.

  • Step 3: Provider websites

Sparse fields, 0% dates, no whole classes to propose. Decide: the same scraped_classes table mostly empty, a business-only path with no classes, or deferred to M3 entirely. Deferring is a legitimate answer and keeps M2 focused on endpoint sources.

  • Step 4: Commit
