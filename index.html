§1What we want challenged

This is a working architecture, not a finished one. The parts most likely to be wrong are named below — argue with those first.

AfterschoolDirectoryUSA is a directory of kids' activities, classes, camps and leagues, Los Angeles County first. The data comes from municipal recreation catalogues, provider websites and an open bulk place dataset — sources we do not control and cannot ask to change. Two runtimes read and serve it: a Python ingestion service and a Laravel application.

The design rests on one promise made to the client and to parents: every published value carries the sentence it came from, and a human decision is never overwritten by a crawl. Most of what follows exists to make that true at the storage layer rather than in a code review.

The four questions worth your time

  1. Is the database a legitimate integration boundary, or are we avoiding an interface we should have written? (§3)
  2. Does an append-only claims log plus a resolver justify its complexity against simply writing rows and keeping an audit table? (§4)
  3. Will Postgres full-text search plus PostGIS hold for a public directory, or are we deferring a search engine we will regret not having? (§7)
  4. Is per-role write ownership worth the friction it adds to every migration and every local environment? (§9)

§2Four decisions everything else follows from

DecisionWhat it meansConsequence if wrong
Python writes to Postgres directly No JSON over stdout, no HTTP endpoint between the runtimes. Two writers to one table. The evidence rule can no longer be enforced in application code.
The database is the seam Laravel inserts a row to schedule work; Python polls for it. Neither process calls the other. No typed contract between the sides. Schema changes become cross-runtime deployments.
Review is exceptions-only The resolver publishes on confidence tier. Humans see conflicts, low confidence, ages, geocode failures. A systematic extraction error publishes at scale before anybody looks.
Published columns are never edited A correction is a new layer-3 claim plus a resolver run — never an UPDATE. Every admin screen needs custom actions; the framework's default edit behaviour is unusable on those fields.

The three layers, which the whole model turns on

Layer 1 is bulk open place data — the spine. Layer 2 is facts read from recreation catalogues and provider sites. Layer 3 is human truth: review decisions and, later, owner claims. Precedence is never reversed. A crawl at layer 2 that disagrees with a layer-3 decision produces a review item, not a write.

Why not an interface between them

Rejected: Laravel invokes Python and parses its output. It keeps a single writer and enforces the claim contract in one place — genuinely good properties, and the Python code was originally written for it. It also couples the runtimes: a Python traceback becomes a PHP job failure, retry semantics must be reasoned about across both, and the pipeline cannot be run or tested without the application present.

Rejected: an HTTP endpoint. Auth, retries and a web request inside the ingestion path is substantial machinery for a single box — and the reach it buys, Python on its own server, the database seam already provides over the private network.

Found in review, not in production

SKIP LOCKED stops two workers claiming the same row. It says nothing about two rows existing for one source — which is exactly what a nightly schedule plus an impatient "re-read this source" button produces. Two crawlers on one host breaks the one-request-per-host politeness rule the project is bound by. The fix is a partial unique index, not more locking.

§4Code flow — the write path

Five hops. Three are Laravel, one is Python, one is a database trigger that neither can talk its way past.

app/Console/Commands/ScheduleIngestionRuns.php

public function handle(): int
{
    $due = Source::query()
        ->where('terms_verdict', 'green')      // only Green sources are ever read
        ->where('next_run_at', '<=', now())
        ->pluck('id');

    PipelineRun::create([
        'source_ids' => $due->all(),
        'status'     => 'queued',
        'reason'     => 'nightly',             // who asked for this crawl
    ]);

    return self::SUCCESS;
}

That insert is the entire invocation. No subprocess, no client, no serialisation format shared with the other runtime.

asd-pipeline — claiming a run

UPDATE pipeline_runs
   SET status = 'running', started_at = now(), worker = $1
 WHERE id = (
       SELECT id FROM pipeline_runs
        WHERE status = 'queued'
        ORDER BY created_at              -- FIFO
          FOR UPDATE SKIP LOCKED
        LIMIT 1
   )
RETURNING id, source_ids;

A composite index on (status, created_at) is not optional here. Without it the claim query scans, and scanning is how a queue becomes the bottleneck.

The evidence invariant, in PL/pgSQL

CREATE FUNCTION claims_evidence_check() RETURNS trigger AS $$
BEGIN
  IF position(NEW.value in NEW.evidence) = 0 THEN
    RAISE EXCEPTION 'claim value % is not present in its evidence', NEW.value;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

Python already drops such claims at construction. The trigger means a bug in Python cannot bypass that: the insert fails, the run fails loudly, and nobody discovers it three weeks later from a parent's complaint.

app/Domain/Claims/Actions/ResolveSubject.php — the only writer of published columns

public function __invoke(string $subjectId): void
{
    $claims = Claim::where('subject_id', $subjectId)
        ->orderByDesc('layer')        // 3 human > 2 catalogue > 1 spine
        ->orderByDesc('confidence')
        ->get()
        ->groupBy('field');

    $publish = [];

    foreach ($claims as $field => $candidates) {
        $winner = $candidates->first();

        // Age never publishes from inference.
        if (in_array($field, Claim::NEVER_AUTO_PUBLISH) && $winner->layer < 3) {
            ReviewItem::open($subjectId, $field, $candidates);
            continue;
        }

        // A lower layer disagreeing with a human decision is a review item,
        // never a write. This is the line the architecture exists to hold.
        if ($this->contradictsHigherLayer($winner, $candidates)) {
            ReviewItem::open($subjectId, $field, $candidates);
            continue;
        }

        if ($winner->confidence < Claim::LOW_CONFIDENCE) {
            ReviewItem::open($subjectId, $field, $candidates);
            continue;
        }

        $publish[$field] = $winner->value;
    }

    Provider::whereKey($subjectId)->update($publish);
}

Read that top to bottom and you have the system. Every branch that is not a confident, uncontradicted claim ends in a review item rather than a write.

The claim is appended, the resolver re-runs, the published column follows. A crawl arriving tomorrow at layer 2 cannot outrank it.

§5Code flow — the read path

One query answers the product's central question: what is on near me, for my child's age, this weekend.

$listings = Provider::query()
    ->select('providers.*')
    ->selectRaw('ST_Distance(l.geog, :origin::geography) AS metres', ['origin' => $point])
    ->join('locations as l', 'l.provider_id', '=', 'providers.id')
    ->whereRaw('ST_DWithin(l.geog, :origin::geography, :radius)', [...])      // GiST
    ->when($q, fn ($qb) => $qb->whereRaw(
        "providers.search_vector @@ websearch_to_tsquery('english', ?)", [$q] // GIN
    ))
    ->when($when, fn ($qb) => $qb->whereExists(fn ($sub) =>                   // composite
        $sub->from('occurrences')->whereColumn('location_id', 'l.id')
            ->whereBetween('starts_at', $when)
    ))
    ->orderBy('metres')
    ->paginate(20);

Three indexes carry it, and each must be proved with committed EXPLAIN ANALYZE output rather than assumed:

IndexServesWhy this shape
GiST on locations.geogRadius and distance orderingGeography type gives metres without projection arithmetic
GIN on search_vectorText searchTakes representative queries from >200 ms to single-digit ms
Composite (starts_at, location_id)"This weekend"Date filtering is a query, not a heuristic — which is why occurrences exist as rows at all

Listings with missing fields are ranked down, never filtered out. Completeness is an ORDER BY term; a parent still sees the listing, with "Unknown" where a value is absent.

Conventions

  • Domain folders mirror write ownership. If a folder needs to write a table another domain owns, the boundary is wrong — that is the smell to look for.
  • Tests mirror the source tree, one to one. A domain folder without a matching test folder is unfinished.
  • Actions over services. Single-purpose invokable classes, named for what they do to what. ResolveSubject, not ClaimService.
  • Files stay small — a few hundred lines. When one grows past that it is usually two responsibilities that have not been separated yet.
  • The claim contract is defined twice, on purpose — once in Python, once in PHP — and reconciled deliberately. Neither side generates the other, because the seam has no build step between them.

The migrations directory holds only Laravel's three stock files, untouched and never run. A verification script asserts zero application tables on the dev server, so a stray artisan migrate is caught rather than assumed.

§7The admin, and why it is not a CRUD panel

Filament gives us the review queue and listing management with no separate front-end build. What it cannot give us is its default edit behaviour.

The constraint that shapes every screen

A form may never write a published column. When a reviewer corrects an age, the panel creates a layer-3 claim and re-runs the resolver — it does not update the row. Stock EditRecord is therefore wrong for exactly the fields reviewers most want to change, and it is disabled on them deliberately.

Three surfaces

SurfaceWhat it doesEditable?
Review queue Claim beside the verbatim sentence it came from — no second lookup, which is the whole return on storing evidence. Accept, reject, or correct. Only by appending claims
Listing management Provider, locations, programmes and their dated occurrences. Shows which layer each published value came from and how confident it is. Read-only + claim actions
Source registry Platform, terms verdict, politeness settings, schedule. Adding a source is configuration, not code. Includes "re-read this source now". Fully editable

What the reviewer actually sees

┌─ Review item ─────────────────────────────────────────────┐ │ Sunrise Gymnastics · age_min │ │ │ │ Proposed 5 layer 2 · pattern · 0.60 │ │ Current (unset) │ │ │ │ Evidence "Classes are open to children aged 5 to 12, │ │ with separate sessions for teens." │ │ Source cityofx.gov/recreation/gymnastics 14 Sep │ │ │ │ [ Accept ] [ Reject ] [ Correct… ] │ └────────────────────────────────────────────────────────────┘

Accepting writes a new claim at confidence 1.00 and layer 3. Nothing in the interface can reach the column directly.

Search, and the decision to defer one

There is no dedicated search index in phase 2. PostgreSQL filters directly at county scale, and a GIN index takes representative queries into single-digit milliseconds. A dedicated engine offers typo tolerance and sub-50 ms responses without tuning — a real advantage we are choosing to defer, on the requirement that adding one later changes a driver and not the call sites.

This is question three from §1. If you think county scale plus faceting will outgrow Postgres sooner than we assume, that is the note to leave.

Layered so that any single mistake — a wrong credential, a bad deploy, a bug in the other runtime — is survivable.

The grant boundary is the one people will fight

Two database roles mean local environments need both, and every migration must grant as well as create. The QA pass connects as the ingestion role and asserts that UPDATE providers is refused — because the failure mode here is silent: someone debugging with the wrong credentials finds everything works, and the boundary is gone with nothing failing.

Backups, and the part people skip

  • Nightly logical dump, encrypted on the machine before it leaves, shipped to object storage. Fourteen nightly, eight weekly.
  • The decryption key is never on the server. A restore requires an operator to bring it and remove it afterwards, so a compromised box cannot read its own history.
  • A restore has been performed, not merely scheduled: decrypt, restore into a scratch database, run a spatial query against the restored data, drop it. Timings recorded.
  • A size floor catches the dump that "succeeds" and writes almost nothing — the failure mode that quietly eats everyone.

Known gap, stated rather than hidden

Nothing pages anyone when the nightly freshness check fails. Wiring alerting now would mean a vendor account outside the client's name, so it lands with the CI work: a scheduled job runs the same check daily and fails the build, which emails. Until then the runbook carries a weekly manual check.

Where to be most sceptical

If the architecture is wrong, we think it is wrong at the seam: two runtimes writing one database with no typed contract between them, relying on grants and triggers to hold a boundary that an interface would hold structurally. Everything else is recoverable. That is not.
